## 设计与根因

| 已观察到的问题 | 本轮组件及行为 |
|---|---|
| 页面选中状态替代了上一轮真正引用的运行 | `application/run_context.py` 区分页面选中、父对话实际答复的 run_ids、点名的运行编号、指标/窗口与版本、最近已完成的执行快照。查询限制在当前研究会话。只有一个匹配项才绑定；多项可行时给出可供选择的编号。入口将绑定理由保存到本轮请求。 |
| 数值解析依赖少数词序，且容易把“低于”和“低于或等于”混在一起 | `application/comparison.py` 从运行级证据读取数值，使用 Decimal 和显式的比较运算符计算。数值关系与用户的条件是否成立分别呈现。支持有符号十进制、中文“负”、阈值在前的部分表达以及已登记尺度上的换算。比例转换为百分比时缩放100；概率差以百分点表示，只有对应差值证据才可采用。同一数值不能仅凭量纲相似被换成另一指标。要求判断是否达标而缺少上限/下限定义时请求澄清。 |
| 数据窗口只留下 4/5 这样的计数 | `plan_scope.py` 对请求区间与已记录的自然日取差集，分别保存请求日期、观测日期、无记录日期及满足合同条件时的缺失日期。数据字典及设置界面新增每日应观察约定及起止日期。没有此约定时，可报告“这个日期没有记录”，不把它断言为应有业务量的缺失，也不补零。 |
| “先解释、再改方案”被路由为单个意图 | `research_service.py` 将已识别的有序请求保留为历史解读与待审计划两部分；`orchestration/research_graph.py` 借用原有节点先记录历史答案，再生成候选。日期条件不清时仍可保留已完成的旧报告说明。界面同时展示“前序报告解读”和新计划。计划本身仍需新批准。 |
| 有历史结果的任务被一律要求远端模型参与才算完成 | 独立评测会话预先锁定校准规则，基于同样的浏览器可见材料、末答、版本、统计数值与实际批准重新评价。外部模型回执、用户停止行为和业务交付分别统计。V2.0、V2.1的原始二元分数原样保存。 |

这种设计不改估计器。只有可追溯的数值才能参与比较；方法咨询、历史结果解释和候选制定都不等于许可计算。每轮证据和新旧运行分开记录。当前文本识别覆盖常见中英文标记及中文研究问法，仍需对未支持的意图和计量单位保持保守。

## 可复核的输出

E盘的以下目录用于分离产品、评分和真实请求。每批均有自己的提交标记和输出目录。

- `eval-runs/rc-close`：可复现失败的初始测试、受影响模块复测、十题逐题和全量回归记录。
- `eval-runs/rc-close-browser`：因T09修正而保留的首候选六题测试。
- `eval-runs/cc-final-browser`、`eval-runs/cc-delivery`：分别为第二候选和最终产品原六题的固定与适应式浏览器尝试、截图、可见文本、实际用量及独立官方冒烟。正式评分与业务复核分列。
- `eval-runs/rc-close-cal`：预登记规则、独立评分代码、历史及本轮逐槽校准。
- `eval-runs/rc-close-holdout`：既有八题与额外独立封存八题的真实本地服务结果；这些不是新的浏览器试用或真人测量。

定向入口为 `tests/test_rc_close_context.py`。工程回归命令为 `python -m pytest -o addopts= -q --tb=short --basetemp=<全新工作目录>`；固定十题由 `python -m causalops.evaluation.v1 --output <全新隔离目录>` 运行。浏览器控制器、原评分器、独立评分器及冻结数据分开保管。不得以正式接口冒烟的请求数代替所有浏览器槽的真实模型调用次数。

## 验收中追加的修正

中间候选在旧八题中已能解释负阈值、等值及缺日，也能形成“先解释旧系数，再制定待审 OLS”的两个有证据的输出。但在 U05/U06 的尾轮，用户询问的是上一研究流程进展，已有的“只说明”规则却会将其路由到方法咨询。最终候选将状态追问绑定至已验证的父流程 ID；已交付的结果和澄清复用当轮数据，并注明来源流程。等待审批时仅陈述当前阶段和方案版本。该路径不执行统计或发起模型请求。对旧提交的独立快照进行了失败复现；不以具体题号、指标名或某个标准答案做分支。

最后十题报告的版本字段保留了 `-dirty` 标志。独立验收核查时唯一未跟踪项是本报告草稿，已跟踪的产品、测试和脚本均与最终提交一致；浏览器使用相同提交的干净归档。最终 94 项受影响测试通过。另有对八种比较运算符、三个带符号数值和三个阈值的 72 组确定性算术检查（单独工程证据，不计任务完成率）。

## 六题的产品变化与评分变化

每个版本分别考察6个固定脚本和18次适应式浏览器尝试（同六题各三次）。下表中的“原→校准”是在同一批原始证据上分别使用两种判据。跨版本同列比较才能观察产品表现变化。校准是独立会话的事后证据复核，审阅者知道既有缺陷，不能称为真人盲审。

|版本 / 流程|分母|业务完成 原→校准|页面 原→校准|末答 原→校准|模拟用户实际闭环|官方请求/回执|可计用户操作；累计槽时长|
|---|---:|---:|---:|---:|---:|---:|---|
|V2.0 固定|6|1→3|4→3|1→1|不适用|29/29|15；309.7秒|
|V2.0 适应式|18|2→5|10→8|2→2|5|54/54|33；639.2秒|
|上一版 V2.1 固定|6|2→4|5→4|3→4|不适用|16/16|15；229.0秒|
|上一版 V2.1 适应式|18|0→18|15→18|12→18|15|0/0|37；419.9秒|
|本轮交付 固定|6|2→4|5→4|3→4|不适用|13/13|15；224.6秒|
|本轮交付 适应式|18|0→18|15→18|12→18|15|0/0|36；438.9秒|

这六题按同一校准量规，业务交付与上一版持平。按冻结原分，后台计算与范围为固定5/6、适应式18/18，未观察到版本审批错误（0/6、0/18）。18个适应式槽均没有生成模型请求，不能作为18次模型生成的正确答案。固定脚本仍有两题无法走完：换指标、改窗口时答复回到旧订单结果。适应式操作的B05、B06均有真实新批准及单独运行。B05原轮看到48条、访客均值76.5833人；B06原轮看到2月11日至17日、7条、订单均值9.71429单。三次B06在交付完整后仍因等待预算退出。另一些历史记录中，模拟器看到一个正确数字就停，但末答和证据不足，校准未给完整分。

校准不要求每题外呼。对于结果题，它要求可见数值、单位、所选来源和用户请求一致，能区分概率、百分点与相对增长，接受等价单位；对变更题还要有正确的新批准、研究口径和运行。不会用先前报告的数字补全新的访客/七日结果。最终文字、页面结果、业务交付与模拟停止分别计分。模型回执只证明一次真实外呼；五个固定槽发生13次，均有HTTP 200与用量，另19槽未外呼。浏览器正式输入40,942、输出1,937 tokens，估价¥0.008567–0.048690，无账单核验。原量规、原分及所有失败留存。

## 真实接口与发布判断

最终单独冒烟使用40行合成表，在官方接口上发出1次逻辑请求和1次物理请求。HTTP 200，取得请求编号与用量回执（7,791输入、430输出）；返回先描述分布、再OLS的候选，因变量quality、自变量acidity，未批准，统计执行数0。物理耗时7.829秒，估价¥0.001876–0.009511，单列于浏览器批之外。一次成功只说明这条真实接口路径可用。

**判断：具备提交候选代码审查的条件，尚不建议升为稳定版本。** 工程回归、旧八题末次追问及运行/批准隔离有实际依据；原六题没有进一步的同量规业务提升，固定的两条变更路径和首次留出集的四项交付缺口仍在。下次稳定版复核应将“范围不匹配时明确停止并解释原因”和“混合请求两部分均可见且分别绑定来源/批准”设为发布条件，用另行封存的问题检验。对模拟用户结束后仍等待的交互问题，应独立校验完成状态的呈现和策略停止条件。未开展真人试用，累计时长不作为真人提效结论。
