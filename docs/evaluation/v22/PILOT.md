## 在页面上观察到什么

1. **第一次进入葡萄酒任务时有两个都像起点的地方。** 页面先显示“当前仅有数据概况”、查看数据质量和推荐研究问题，随后才出现已算出的质量评分预览及“生成完整描述统计报告”。数据并未丢失，但知道按钮的脚本无法衡量新用户要读多久。下一轮可从相同空首页测量首次有效动作和是否误入制订计划。
2. **错误文件能安全恢复，但指引相互矛盾。** 已选 bad.csv 时页面同时显示“列名为空或重复，请先修正文件表头”和“选择文件后显示真实行数、字段类型与缺失情况”。禁用创建是正确的。后续改进可让提示直接说明“请更换修正后的文件”，并在换好后展示文件名和新的行数。本次恢复者已获修正版，不包含用户独立修复 CSV 的时间。
3. **报告任务容易低估导航成本。** N04 起点已在审核页，并已在案例页确认过实验来源。三个操作衡量的是最后一段。用这条数字代表“首次访客从首页完成营销研究”会漏掉数据获取、理解分组、核对字段、找到审核入口等成本。
4. **故障层级须分开。** N08 是可预期的数据校验失败；刷新同一 URL 后仍能恢复已建任务。它没有验证断网、进程崩溃、审批提交中断或文件上传一半时的恢复。

## 既有运行器检查与证据边界

V2.0 的 controller 负责构建测试库和事后核验；browser/drive.py 用真实浏览器交互并保存 DOM 观察、截图、错误事件，还包含固定脚本与基于可见控件的策略。其典型起点是预先准备的研究会话，入口常直接打开含 sid 的 URL，不能直接测量首页发现成本。V2.2 复制了协议而非研究数据，复用了启动器、浏览器加载和捕获实现。新增 action 日志把“尝试派发”与“控件成功接收”分开。计时用 perf_counter，绝对时间另记 UTC。使用评测机原有环境，无需向服务商发送数据。

三次操作完结后，控制器用只读连接独立核对了专用工作区中的审批和运行数；浏览器操作者不读取数据库、隐藏答案或内部接口。完整输出目录在本地，不提交工作区、数据库、下载文件或截图。可复跑入口见[冻结协议](PROTOCOL.md)。证据文件：summary.json 为整批记录，postrun-check.json 为独立核验，各题内含 actions.json、browser-events.json、result.json、起止页面文字及截图。N08 另存 rejection.txt，N04 另存 export.html。

## 下一步的实施顺序

先给 N01、N03、N05–N07 补上固定脚本和独立判据，尤其是历史报告选择、换指标与换窗口的审批绑定。再增加“找错入口、返回、首次找到正确控件、恢复前后的研究编号”事件，分开报告页面等待、阅读/决策与操作时间。最后才启用隔离的自由探索：仅给题面、公开附件和浏览器观察，限制操作预算；首次尝试与重试分别保留，控制器独立判分。未观察的求助、主观理解和真人耗时保持未测。
