# 下一代产品需求候选（尚未实施）

本清单是V2.3结项后的需求输入，不是已实现功能说明、开发承诺或本轮执行计划。

优先级含义：P1先做需求验证与范围确认；P2依赖基础能力、按具体用户场景推进。现有研究解释风险在选定场景中必须先获得明确处理策略，不能靠新增框架掩盖。

|需求候选|已有基础|新增或实质扩展范围|优先级与理由|
|---|---|---|---|
|多步骤研究规划|Plan最多5步、注册工具执行、版本化审批；支持部分明确混合请求|可执行步骤依赖、输入/输出绑定、中间结果核对、用户目标逐项覆盖；超出工具能力时明确拒绝|P1。解决“文字方案与实际计算不一致”，先限单表、少量受支持步骤|

## 1. 多步骤研究规划的最小候选范围

目标：把一个有限研究问题分成可审查、可执行、可追溯的步骤，而不是只列几个方法名称。

- 输入：用户目标、已确认合同、现有工具合同。
- 输出：结构化步骤及顺序、每步输入/输出、筛选/分组/窗口、缺失条件、待审版本。
- 必须区分“会做”“需要补充”“当前不支持”；不把算子写进理由文本当成已配置。
- 可以复用现有Plan和研究服务；是否增加依赖字段须先做设计，不默认更换LangGraph或新增Agent团队。
- 候选验收：每个批准步骤与实际工具参数一致；改变指标/窗口使相关批准失效；不能执行的步骤有具体原因；旧运行不覆盖。
- 不包含：任意代码生成执行、自主批准、跨任意数据源研究、自动选择有利结果。

## 2. 主动诊断的最小候选范围

目标：在已保存诊断和数据合同支持下，解释问题并提出可核对的下一步。

- 诊断事实与研究假设分开；缺少随机化依据不能自动标随机。
- 修订需列原值、新值、理由、受影响的数据和结果。建议不等于研究事实已确认。
- 可以建议补充样本信息、改用受支持描述路径或停止；不自动填补数据、改分母或改变纳入人群。
- 候选验收：每项建议有实际诊断来源，接受后另建版本重新审查，拒绝建议不改变原研究。
- 不包含：自动修到“通过检验”、根据显著性挑选模型、用模型文本覆盖已登记业务语义。

## 3. 多表数据的最小候选范围

目标：在一项研究中声明两表关系并核对连接后粒度。

- 先支持一种明确两表场景，显示键缺失、键重复、连接前后行数及不匹配数量。
- 连接关系和纳入规则需用户确认；多对多不能静默膨胀并直接计算人均指标。
- 版本化连接配置、源数据指纹、目标指标分子分母及历史结果来源。
- 候选验收：一对一、一对多和不合法多对多可区分；版本替换使批准过期；相同数值不同字段不会混用。
- 不包含：分布式数仓、跨企业权限系统、任意SQL执行、云端多人协作。

D09/E10的未执行只是需求线索，不应把改造后在这两题通过称为新的独立泛化验证。

## 4. RAG专项的最小候选范围

目标：判断是否检索到当前问题需要的适用条件和限制，而非增加知识库规模。

- 记录查询、命中文段、出处版本、适用研究条件与最终引用。
- 将未召回、召回无关、引用不支持结论、生成忽略证据、校验失败分别归因。
- 检索不足时保留解释和明确缺失依据，不无限重试，也不编造引用。
- 候选验收：预先定义独立检索问题与人工参考；报告条件覆盖、引用支持和失败恢复，生成质量另测。
- 不包含：本轮下载全文文献、重建向量数据库、假定接入新框架自动改善研究能力。

## 5. 共同前置条件

1. 先选择科研或企业业务中的一个具体主场景及可支持的数据边界。
2. 明确统计口径错误的处理：缺少条件则澄清；已知冲突则阻断；不能只检验JSON合法。
3. 新能力必须沿用人工审批和不可变运行证据，不以便利性降低授权。
4. 旧开发/保留题全部保留，只作为已使用回归材料；未来新评估需另行冻结，不能追溯改分。
5. 浏览器导航与研究正确性分别验收；模拟用户不能替代真人研究人员。
6. 先解决所选场景的高风险约束，再讨论新增方法、性能或部署规模。

建议顺序：确定单表主场景 → 明确步骤/指标/诊断合同 → 小范围规划与诊断能力 → 有任务依据的两表支持。RAG专项测量可作为独立工作流，但不因本清单自动启动。

## 6. 对外表述边界

可以表述：已有带版本化方案、人工审批、统计工具和运行证据的本地研究工作台；已建立包含失败与争议的Agent评测体系。

应限定表述：多步骤执行和结果问答在受支持设计内可用，开放式任务仍存在研究语义与交付限制。

不能表述：已实现通用自主研究规划、主动修复任意研究、多表自主分析、全面优化的RAG、生产级多用户平台或已证明真人效率提升。

本清单全部为后续候选，不在本轮实施。
